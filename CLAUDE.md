A time window alone is the wrong instrument: compose, type three more characters, press Enter, and a fast typist is still inside any window wide enough for a slow one, so the send gets eaten (proven — reverting the consume-on-next-keydown line fails on `a deliberate Enter stopped sending`, not on the IME assertion). The 100ms bound stays only so a stale marker cannot survive the user composing, clicking away, and returning minutes later. The guard sits in the SEND handler, not the capture guard, because the named harm is "clicks Send while the user is only accepting a candidate" and Enter must keep reaching the page by design. Registration order matters and is deliberate: the bookkeeping listener registers before the narrow capture guard on the same node and phase, so it always sees the event the guard is about to `stopImmediatePropagation`. **Round 10 then narrowed the ARMING, because round 9's version was a net regression that shipped through a fully green suite.** It armed on EVERY `compositionend`, which is right only for WebKit's inversion; every conforming browser fires the commit Enter FIRST (with `isComposing` true) and `compositionend` after, so the marker armed AFTER the commit and pointed at the user's next keystroke — a deliberate Enter within 100ms vanished silently. That trade is strictly worse than the bug being fixed: WebKit's costs a stray send to CJK users on one browser, this cost a swallowed send to EVERYONE on every other. Arming is now gated on `ravenCommitEnterAlreadySeen`, set (assigned, never OR-ed, so a character key clears it) on each keydown that is an Enter with `isComposing` true. One residual is documented rather than hidden: accepting a candidate with the MOUSE also ends composition with no commit Enter, so it arms — indistinguishable from WebKit's ordering by construction. The 100ms bound was deliberately NOT tightened, because WebKit is banned on this host and the timing cannot be measured. **Round 11 narrowed it three more times, because `compositionend` does not mean "committed".** The UI Events spec fires it on cancellation too — Escape, blur, focus change, IME dismissal — so round 10's version armed on an Escape-cancelled composition and ate the very next Enter, the same class of bug one layer in. (1) Arm only when `event.data` is a NON-EMPTY string: a cancellation carries `""`, a commit carries the committed text, and that is the only discriminator the spec hands you. (2) Record the origin from `composedPath()[0]` and honour the marker only when the keydown's origin matches — **not `event.target`**, because from `window` a shadow-tree target retargets to the host, which makes every element inside the overlay indistinguishable and let one field's composition absorb another's Enter. (3) Stamp the verdict PER-EVENT rather than on a module global, which anything running between the bookkeeping listener and the send handler can disturb — including a page capture handler that synchronously dispatches another keydown. **Round 12 fixed HOW that verdict is stored, because round 11 put it somewhere the page can reach.** It was an own property on the event (`event.__ravenCompositionCommit`), and a page listener can `delete` it or write `false` onto it — worse, a page that calls `Object.preventExtensions(event)` in a window-capture listener makes the assignment THROW, and this file is `"use strict"`, so the throw kills the rest of that listener including the `ravenCommitEnterAlreadySeen` update on the next line (Sol proved it with a live `TypeError: Cannot add property __ravenCompositionCommit, object is not extensible`). It is now a module-private `WeakSet` closed over by the overlay IIFE: the page holds no reference to it, `WeakSet.add` works fine on a non-extensible object, and it is still strictly per-event. Do not "simplify" it back to a property — the whole point is that the page cannot see it. **Round 13 corrected that claim, which was true of the SET and false of the OPERATIONS, and closed two more holes of the same shape.** (a) `WeakSet.prototype.add/has/delete` are ordinary page-realm properties: a page that swaps them out reaches the verdict without ever naming the set — make `has` return false and every IME commit reads as a deliberate send. The three are captured at load via `Function.prototype.call.bind`. What that does NOT buy, and the comment now says so instead of claiming immunity: a `<head>` script poisoning the prototype BEFORE injection still wins, which is unclosable from inside a shared realm. (b) The verdict is CONSUMED on read — a `KeyboardEvent` can be dispatched more than once, and an unconsumed mark let a page replay the user's own commit Enter forever, swallowed every time. One mark, one suppression. (c) **The 100ms bound was not a bound**, because `performance.now` is page-replaceable and the expiry is a subtraction over two of its readings: hand back a large value at `compositionend` and a small one at a much later Enter and the delta is NEGATIVE, which satisfies any `< 100` test forever. `performance.now` is captured at load AND `ravenElapsedSince` returns `Infinity` on a delta that is not a non-negative number — the arithmetic half is the load-bearing one, since a pre-injection swap defeats the capture but not the sign check. **Round 14 then showed the sign check was necessary and never sufficient, and corrected one claim that was simply wrong.** (a) A CONSTANT clock defeats it more simply than a backward one: `performance.now = () => 0` makes every delta exactly `0 - 0`, which is non-negative and passes `< 100` forever. The stamp now records BOTH clocks and elapsed time is the **larger** of the `performance.now` and `Date.now` deltas, so a page must freeze both, pre-injection, to hold the window open; taking the larger also preserves the backward-clock behaviour, since `Infinity` wins. The accepted cost is stated in the comment rather than discovered later: `Date.now` is wall-clock and can step, so an NTP jump of >100ms landing between `compositionend` and the commit keydown expires a marker that should have held — the same false-negative direction the bound already accepts, and rarer. (b) **The overlay no longer claims the verdict is safe from a hostile page, because it is not and never was.** Raven's shadow root is OPEN, so a page reaches the field through `shadowRoot` and dispatches a synthetic `compositionstart`/`compositionend` pair that arms the marker without touching any prototype — it feeds the mechanism rather than tampering with it, which the WeakSet capture does nothing about. `event.isTrusted` on the arming `compositionend` would close it and is deliberately NOT used: a page that can dispatch into the shadow root can also `remove()` the host, read every keystroke in the panel, and synthesise the Send click, so the forged verdict (which only ever SUPPRESSES one Enter) is strictly less than what that attacker already has. **This guard is a correctness mechanism against the browser's own event ordering, not a security boundary against the page** — the open shadow root means there is no such boundary to hold. `compositionstart` clears both pieces of state, so a commit in the PAGE's own field cannot disarm Raven's next composition. FOUR residuals are documented in the comment rather than papered over: a mouse-selected candidate, an IME that reports raw pre-edit text as `data` on cancel, a page script that registers a window-capture `compositionend` listener before the overlay loads and calls `stopImmediatePropagation()` (that one cannot be closed from inside the page, only noted), and — added in round 12 — the 100ms bound's own false negative for a very slow typist. **Sol argued the clock is now pure downside and it was kept anyway, deliberately:** ordering does decide the verdict, but without the bound the mouse-selected-candidate residual becomes UNBOUNDED IN TIME (accept a candidate with the mouse, walk away, come back minutes later, press Enter, send eaten), and clearing on blur/`pointerdown` does not rescue it because an IME candidate popup is OS chrome that fires no DOM event in the page. A bounded false negative for a slow typist beats an unbounded one for every mouse-using IME user. `test/grab-overlay-key-isolation.test.mjs` (16 tests) makes each mechanism independently falsifiable (delete the capture guard → test 1 red; delete the host guard → test 4 red; re-add the 229 clause → the Android test red; delete the send-handler guard → the IME commit assertion red; make the marker clock-only → the deliberate-Enter assertion red; delete the `ravenCommitEnterAlreadySeen` early-return → the conforming-ordering test red and ONLY that one, with the WebKit test still green; drop the empty-`data` check → the ESCAPE-cancelled test red; drop the origin match → the different-element test red; drop the `compositionstart` clear → the page-field test red; revert the `WeakSet` to an event property → the two round-12 tests red and ONLY those two; look the `WeakSet` methods up on the prototype at call time instead of capturing them → the prototype-tampering test red; drop the consume-on-read → the redispatch test red; make `ravenElapsedSince` a raw subtraction → the backwards-clock test red; make it consult `performance.now` alone → the frozen-`performance.now` test red and ONLY that one; make it take the SMALLER of the two deltas → BOTH clock tests red, which is what separates MAX from MIN and is why there are two clock tests rather than one — each measured, each hitting exactly one test unless noted) and needs real Chromium. **The redispatch test had to be rewritten before it could detect anything:** the first draft dispatched a SECOND freshly-constructed event, which was never marked in the first place and therefore sails through whether or not the verdict is consumed — it passed against the defect. ## Target customer (customer-lens-kickoff, 2026-07-09; evolved 2026-07-12)

### Primary lens — the paying team (2026-07-12)
- We are a product/design team (designers + engineers) with an existing design practice and shared tooling (Slack, Figma, a design system in some state of maturity)
- We are trying to make our design decisions, taste, and system knowledge durable and enforceable across people and AI agents
- But our decisions live scattered in Slack threads, meeting notes, and heads — they get re-litigated and lost
- Because no tool maintains a living, queryable decision/taste graph that both humans and coding agents consult
