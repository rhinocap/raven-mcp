One residual is documented rather than hidden: accepting a candidate with the MOUSE also ends composition with no commit Enter, so it arms — indistinguishable from WebKit's ordering by construction. The 100ms bound was deliberately NOT tightened, because WebKit is banned on this host and the timing cannot be measured. **Round 11 narrowed it three more times, because `compositionend` does not mean "committed".** The UI Events spec fires it on cancellation too — Escape, blur, focus change, IME dismissal — so round 10's version armed on an Escape-cancelled composition and ate the very next Enter, the same class of bug one layer in. (1) Arm only when `event.data` is a NON-EMPTY string: a cancellation carries `""`, a commit carries the committed text, and that is the only discriminator the spec hands you. (2) Record the origin from `composedPath()[0]` and honour the marker only when the keydown's origin matches — **not `event.target`**, because from `window` a shadow-tree target retargets to the host, which makes every element inside the overlay indistinguishable and let one field's composition absorb another's Enter. (3) Stamp the verdict PER-EVENT rather than on a module global, which anything running between the bookkeeping listener and the send handler can disturb — including a page capture handler that synchronously dispatches another keydown. **Round 12 fixed HOW that verdict is stored, because round 11 put it somewhere the page can reach.** It was an own property on the event (`event.__ravenCompositionCommit`), and a page listener can `delete` it or write `false` onto it — worse, a page that calls `Object.preventExtensions(event)` in a window-capture listener makes the assignment THROW, and this file is `"use strict"`, so the throw kills the rest of that listener including the `ravenCommitEnterAlreadySeen` update on the next line (Sol proved it with a live `TypeError: Cannot add property __ravenCompositionCommit, object is not extensible`). It is now a module-private `WeakSet` closed over by the overlay IIFE: the page holds no reference to it, `WeakSet.add` works fine on a non-extensible object, and it is still strictly per-event. Do not "simplify" it back to a property — the whole point is that the page cannot see it. `compositionstart` clears both pieces of state, so a commit in the PAGE's own field cannot disarm Raven's next composition. FOUR residuals are documented in the comment rather than papered over: a mouse-selected candidate, an IME that reports raw pre-edit text as `data` on cancel, a page script that registers a window-capture `compositionend` listener before the overlay loads and calls `stopImmediatePropagation()` (that one cannot be closed from inside the page, only noted), and — added in round 12 — the 100ms bound's own false negative for a very slow typist. **Sol argued the clock is now pure downside and it was kept anyway, deliberately:** ordering does decide the verdict, but without the bound the mouse-selected-candidate residual becomes UNBOUNDED IN TIME (accept a candidate with the mouse, walk away, come back minutes later, press Enter, send eaten), and clearing on blur/`pointerdown` does not rescue it because an IME candidate popup is OS chrome that fires no DOM event in the page. A bounded false negative for a slow typist beats an unbounded one for every mouse-using IME user. `test/grab-overlay-key-isolation.test.mjs` (11 tests) makes each mechanism independently falsifiable (delete the capture guard → test 1 red; delete the host guard → test 4 red; re-add the 229 clause → the Android test red; delete the send-handler guard → the IME commit assertion red; make the marker clock-only → the deliberate-Enter assertion red; delete the `ravenCommitEnterAlreadySeen` early-return → the conforming-ordering test red and ONLY that one, with the WebKit test still green; drop the empty-`data` check → the ESCAPE-cancelled test red; drop the origin match → the different-element test red; drop the `compositionstart` clear → the page-field test red; revert the `WeakSet` to an event property → the two round-12 tests red and ONLY those two) and needs real Chromium; an earlier version listened in bubble phase only and passed with the capture guard deleted. The conforming-ordering test asserts its own fixture — that `isComposing` read back `true` — because a Chromium that stopped honouring the init member would otherwise turn the whole case into a silent pass. ## Target customer (customer-lens-kickoff, 2026-07-09; evolved 2026-07-12)
**Strategic evolution (Andrew, 2026-07-12; boundary clarified 2026-07-18): the TEAM is now the primary customer.** The team paid service is **Morven**, a separate superset product (all of Raven is in Morven; not all of Morven is in Raven) — Raven itself stays the free open-source tier serving the solo indie dev forever. Judge new features through the team lens first (shared workflows, multi-user consent, admin approval, org data handling), while never regressing the indie dev's free "under a minute" path. New-feature kickoffs default to asking the delta question against BOTH lenses.

### Primary lens — the paying team (2026-07-12)
- We are a product/design team (designers + engineers) with an existing design practice and shared tooling (Slack, Figma, a design system in some state of maturity)
- We are trying to make our design decisions, taste, and system knowledge durable and enforceable across people and AI agents
- But our decisions live scattered in Slack threads, meeting notes, and heads — they get re-litigated and lost
- Because no tool maintains a living, queryable decision/taste graph that both humans and coding agents consult
- Which makes us feel like we're paying a coordination tax on every project
- Meets the product: via a team member (often the indie-dev free user) advocating internally; evaluated with IT/admin approval, procurement, and data-handling questions in the room
- Bounces on: anything requiring broad data access without clear consent controls, unclear data retention/LLM handling, per-seat pricing with no obvious team-level win over the free tier

### Free tier lens — the solo indie dev (2026-07-09, retained verbatim)
- I am a solo indie developer/builder, working alone, moderately technical but not deep into the design-tooling space
- I am trying to figure out whether this "design-intelligence MCP server" thing is worth adding to my coding-agent workflow
- But I've never heard of this category before landing here — I don't yet know what an MCP design/taste server even does
- Because design-intelligence-for-AI-agents is a new, unfamiliar product category — there's no existing mental model to slot this into
- Which makes me feel skeptical and a little impatient — is this real, or is it AI-marketing fluff?
- Meets the product: cold, via GitHub/HN/Twitter discovery, no prior context, evaluating solo with no one to ask
- Bounces on: a site that looks less polished than competing tools (undermines the "design intelligence" claim on its face), vague AI-marketing copy that never says concretely what it does, no obvious "try it in under a minute" path
- Expects voice: plain, concrete, show-don't-tell — a working example or before/after beats an adjective-laden pitch; technical enough to trust, not jargon-dense
- Uncalibrated: none — all three interview questions answered
