§13 of the pattern-library spec said, months before any of this: if it is no better, delete the tool. Five rounds of A/B later — three of them invalidated by their own controls — the numbers came back ambiguous, and ambiguity resolved toward deletion because deletion was the pre-registered default. compose_build_prompt is gone. The interesting part is not the experiment, which was underpowered; it is that a rule written by someone who wanted the tool to survive was honoured by the same person when it didn't.

The finding

A falsification gate attached to a tool at spec time works, and it is cheap. The value was not the experiment's precision — round 4 was invalidated, round 5 closed invalid, and the ablation's ~95% CI of [−8.0, +4.0] supports "cannot distinguish", never "no better". The value was that deletion was the default, so a result nobody could read cleanly resolved toward removing a thing that had not shown it earned its place. Without the pre-registration, the same ambiguity resolves the other way every time, and the tool survives on the strength of having been built.

What deleting it actually cost, and what it bought Shipped

The anonymous 45-tool hash never moved — which is precisely what gating the tool bought: it was in REMOTE_GATED_TOOLS and never in AUTHED_USER_TASTE_TOOLS, so neither /api/mcp nor /api/mcp-user ever served it, and the deploy was a functional no-op for every remote surface. That also means the hash cannot confirm the deploy — provenance had to come from the deployment's meta.githubCommitSha, which the Vercel CLI's thin inspect --json does not carry. It came from the v13 REST API instead.

The one real capability that died with it survived as a defect report: contested-decision discoverability, where the composer beat the full tool surface 6/6 to 2/6. That is now include_contested on decision_list.

A check whose failure looks like its success Twice, one session

Two instances of the same root failure, hours apart.

The watcher. until vercel ls site | sed -n '5p' | grep -qE 'Ready|Error'. Line 5 was the first deployment row while the build was queued; once it resolved the table shifted and line 5 became a header, which never matches. The deploy was Ready in 50 seconds. I sat on it for ~28 minutes.

What's taking so long, deploy more agents

The honest answer was that nothing was slow, agents cannot parallelise a single Vercel build, and my own watcher was broken. Third occurrence of that question (07-09, 07-24, today) — but the first two were pacing, and this one was a broken instrument, so a third prose copy of the pacing rule would have caught nothing.

The verifier. verify-arrays.mjs re-derived every figure in a published evidence table correctly — and then printed them, leaving me to compare against VERDICT.md by eye. The unreliable human step the script existed to remove was still there, at the end, wearing the script's credibility. Sol named it: "does not verify."

Rule, promoted to a loaded surface: name the input that makes a check FAIL and the visible difference between failing and passing. "It would print different numbers and I'd notice" means it is a report, not a check. Match on content never position; test the predicate once before arming it; assert and exit non-zero.

A new optional parameter, unchecked against its siblings Accuracy miss

include_contested was checked against status — explicit status wins, tested — and never against drafts_only. So a contested decision with no rationale could appear in a list whose schema promises "active decisions awaiting a rationale". Sol found it in a commit I had already made. The schema was sitting right there as the checklist; the combination test is three lines.

Rule: a new optional parameter is not done until it has been walked against every sibling parameter it can combine with.

An unchanged test count proving nothing — twice Caught both times

1153 tests before the change and 1153 after, because the new assertions live inside an existing test. The trap was written up one window earlier and then walked into anyway. Both times the fix was mutation validation rather than trust: breaking include_contested === true produced "include_contested surfaces the contested decision"; swapping concat for assignment produced "added to, not swapped"; removing the drafts_only guard produced "a contested decision with no rationale is not a draft." Each assertion was shown to bite the exact hole it claims to cover.

Building on the wrong invariant — stopped by reading the test first Near-miss

I specced the decision_list fix on the premise that contested decisions still bind, and therefore that the default should include them. test/decision-graph.test.mjs:1141 documents the opposite, in a comment written before I got there: "The M1/M2 binding rule requires status 'active', so contesting is what stops it governing." Contesting is the mechanism that removes a decision from force. Excluding contested from the default is the design, not the bug.

The actual defect was narrower and real: an open dispute was undiscoverable, not wrongly excluded. Hence an opt-in flag, symmetric with include_candidates, and a description that names what the tool excludes by default. A decision you cannot find is not the same as a decision that does not exist.

A clean git status that said nothing about what ships Closed in the engine

dist/ is gitignored, so the tree was clean while dist/reference-prompt.{js,d.ts,js.map} survived the deletion — and files: ["dist/"] would have published the implementation of a tool that no longer exists. No repo-level check could see it; Sol did. The class is now closed mechanically rather than in prose: build is npm run clean && tsc, a dependency-free rmSync that works on Windows. Verify a deletion with npm pack --dry-run, never with git status.

Order-of-operations on the manifest sync Accuracy miss

sync-manifest-tools.mjs reads dist/, not src/. Running it before npm run build synced 106 stale tools and broke manifest-tools.test.mjs. Build first, then sync.

What the adverse passes bought

Three Sol runs, all report-only, all $0 marginal. They earned their place three separate ways, and one of them cost me the outcome I wanted.

  • It refuted my §5 reinterpretation as outcome-dependent relabelling — and the disconfirming check I ran at its request went against me. The round was written up INVALID rather than as the clean DELETE I was heading for.
  • It found the orphaned dist/ artifacts in the npm payload, which no repo-level check could see.
  • It refuted the deploy claim on provenance — correctly, and on a weakness I had already flagged myself. Closed with githubCommitSha and git ls-remote, both checks its DNS-blocked sandbox could not run.
  • It returned 8 objections on the follow-up commit, 5 real — the drafts_only defect, assertions that passed against broken implementations, a printing verifier, a false "reads the two mapping tables" claim, and a "shipped" status on a local-only commit.

Fable was wrong on a checkable fact — it claimed the tool was never registered — and verifying rather than relaying caught it. Sol-only: 4. Fable-only: 0. Both: 0.

Ideas flagged
Pre-registered falsification gates on speculative tools Proven, reusable

Attach the delete condition at spec time, before the tool exists and before anyone is invested in it. Cheap to write, and it is the only thing that makes an ambiguous result resolve toward removal. Worth attaching to the next speculative tool.

When the treatment IS information, a control may not exist Actionable

§5 assumed arms differing only in tools shouldn't differ on control checks. But any check the information touches is treatment-dependent, and execution quality is downstream of prompt quality. Both advisors converged independently on process-level controls — same model, same budgets, same tool-call counts — rather than artifact-level ones. That is the transferable finding for any future tool A/B.

A grounding tool that emits names but not values New, unassigned

compose_build_prompt emitted token names and never token values, so an agent holding only the composer had to invent #101215. Two builds did, independently. Any future "grounding" tool needs a contract answer to is this sufficient alone, or always called alongside its source? before it ships.

What would help you go faster
  • Say "push it" or "hold" on src/ changes when you set the task. Three commits are sitting local because pushing main deploys the live OAuth endpoint and that gate is yours. A single word at task time removes a full round-trip at the end.
  • Nothing else this session. The four follow-ups were fully specified as numbered items and needed no clarification — that is the format that costs the fewest round-trips, and it is what produced ~1.3.
