Accuracy gap

Videos black on Andrew's XDR

The lazy-loader appended webm (VP9) first, then mp4. Calling v.load() clears the poster, so while the large file was still buffering the screen showed pure black. This was invisible to every static check (posters rendered fine in Playwright; Raven's audit_page returned unloaded_video_artifacts: [] because it waited for settle). Andrew had to see it on the deployed URL on his real machine to catch it.

RULE (new — should be added to CLAUDE.md): For lazy-loaded autoplay video on a marketing page: (1) mp4/h264 ONLY in the source list — no webm first (h264 is universal; VP9 buffering kills the poster). (2) Poster image as a CSS background-image behind the <video> screen container — never relies solely on the poster attribute. This way no decode state (pre-load, error, slow buffer, codec-fail) ever shows black. NOTE: Cannot edit CLAUDE.md in headless revisit. Flagged for manual promotion.

Accuracy gap

Wrong verification viewport (XDR)

Verified the full-bleed layout at 2560px (Playwright) and reported "device=1320px, no overflow, text correct." On Andrew's actual Studio Display XDR the full-bleed + 1320 cap stranded the text track in a vast empty expanse, and the layers grid had an orphan. The XDR is 5120px native; at 2x CSS pixel ratio that's 2560px — so I was right at the boundary and missed what happens at 2700–3000px CSS widths.

RULE: When the user is on an XDR/5K/ultra-wide display, Playwright verification at 2560px is NOT sufficient. Always sweep: 2560, 2736, 3000, and ask Andrew which CSS width his display runs at. 2560 is the edge; XDR behavior can diverge. Already in CLAUDE.md: "Reproduce on the user's surface." Execution failure.

Accuracy gap

Raven contrast audit false-positive reported as real failures

In the brand-profile + P1 fix pass, audit_contrast reported 78 AA fails (install pill at 1.08:1, sub-labels at 3.46:1 — alarm-level numbers). The true parent-chain compositing showed 0–20 real failures. I had to write a custom DOM-walk script to determine which were real. Raven was compositing rgba() backgrounds over a light white canvas instead of the actual dark ancestor.

RULE: When audit_contrast returns a high fail count on a dark-theme page, verify a sample via true parent-chain compositing in the browser before acting on the numbers. A "1.08:1" on a dark page is almost certainly a compositing artifact. Already logged in raven-opportunities.md as P1 fix for the Raven repo.
