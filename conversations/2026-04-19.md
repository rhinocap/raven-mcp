### Self-audit of the demo pages
**What:** Ran `audit_page` against all 6 demos on ravenmcp.ai. Every demo scored 100/A but had 3–5 warnings each — so the grade itself is misleading. Universal findings:
- `spacing/scale-count` fires on all 6 demos (11–24 unique spacing values vs target 5–7)
- `tokens/no-bare-hex` fires on all 6 (mix of real signal + rule noise from rgba)
- `spacing/base-unit` fires on 5/6 (values off 4/8px grid)
- `typography/line-height-scale` fires on 3/6

**The meta-finding:** Raven's best-case output fails Raven's own rules on spacing discipline and modular typography. Claude reaches for visual variety over systematic tightness unless explicitly constrained. This is exactly the kind of gap that should be captured as a new principle.

### Full end-to-end release automation
**What:** Built the pipeline Andrew described: any time new knowledge lands (via community PRs or Raven's own self-audit), release + notify + changelog all run automatically on Friday. Five pieces:

1. **Friday release workflow** (`.github/workflows/release.yml`)
   - Cron `0 17 * * 5` + manual dispatch.
   - `scripts/detect-release-scope.mjs` scans merged PRs since the last tag, reads labels (`breaking`/`major` → major, `feature`/`minor` → minor, default patch), generates release notes grouped by category.
   - Calls existing `scripts/release.sh` to bump version, sync `manifest.json`, rebuild `.mcpb`, `npm publish`, commit, tag, push.
   - Attaches `raven.mcpb` to the GitHub Release as a downloadable asset.

2. **Changelog page** (`scripts/build-changelog.mjs` + `site/changelog.html`)
   - Pulls last 30 non-draft/non-prerelease releases via `gh api repos/.../releases`.
   - Minimal markdown → HTML renderer (headings, lists, inline code, bold, auto-linked issue refs).
   - Static generation at release time. Survives GitHub outages. Added `Changelog` to the main site nav.
   - Built locally; empty state renders ("first release is on its way") until Friday's cron.

3. **Self-audit cron** (`.github/workflows/self-audit.yml` + `scripts/self-audit.mjs`)
   - Cron `0 16 * * 0` (Sundays, so Monday's knowledge-PR workflow picks up whatever it files).
   - Spawns Raven as a subprocess via the MCP SDK's `StdioClientTransport`, runs `audit_page` on each demo in `site/demos/`, aggregates warnings by rule, filters to rules appearing in ≥3 demos.
   - Asks Claude Opus 4.7 (with prompt-cached system prompt) which recurring warnings are real knowledge gaps vs rule-refinement needs, and drafts a GitHub issue body for each gap.
   - Fuzzy dedupe against open `knowledge-request` issues (token overlap > 0.6) before filing.
   - Separates "knowledge gap → file issue" from "rule refinement → log only" so the pipeline doesn't file an issue every week demanding we fix the audit rule itself.

4. **Email release notification** (`scripts/notify-release.mjs` + `api/welcome.js` update)
   - `notify` job runs only when bump ≠ patch.
   - `api/welcome.js` now fire-and-forget subscribes each `raven_register` caller to the Resend audience (`RESEND_AUDIENCE_ID`). Doesn't fail registration if the audience add fails.
   - `scripts/notify-release.mjs` creates a Resend broadcast to that audience, renders release notes from the detect-release output into branded HTML, and sends.

5. **In-product update check** (`src/index.ts`)
   - On startup, fetches `registry.npmjs.org/raven-mcp/latest` with a 3s timeout.
   - Compares versions. Only fires the banner for minor/major bumps (patch stays silent).
   - Logs to stderr AND monkey-patches `server.tool()` to prepend a one-line banner to the first tool response of the session.
   - Never blocks startup. Catches all errors (offline, blocked, rate-limited → silent).
   - Opt-out via `RAVEN_NO_UPDATE_CHECK=1`.
   - Fixed stale `version: "1.0.0"` hardcode — server now reports the real `package.json` version.
   - Smoke-tested locally by pinning a fake version to 0.1.0 and confirming the banner appeared in both stderr and the first tool response.

**Why:** Andrew wants "any time there is something worth adding, then pushed to npm or wherever else so people can get the latest version, a way to notify them of the latest version, and a section in the docs to show what the latest updates were." This delivers all four in a human-gated loop: Claude drafts → Andrew merges → Friday ships automatically → users get email + in-product notice + updated changelog page.

## Mistakes & lessons
| Mistake | Type | Rule added |
|---------|------|-----------|
| First pass instructed Andrew to add a secret to GitHub without saying "not into chat" — he pasted a live API key into the conversation. Had to be revoked. | Comm gap | Saved feedback memory `feedback_never_paste_secrets_to_chat.md`. Every future secret instruction must explicitly say where it goes AND that it must not pass through chat. |
| `gh release list --json` was assumed to expose `url` and `body` fields — it doesn't. First changelog build failed on "Unknown JSON field". | Accuracy gap | For gh CLI JSON queries, verify field availability via `gh <cmd> --json <bogus>` to get the error-listed field set before relying on fields in a script. REST API via `gh api` is usually fuller than the JSON flag. |
| `gh pr create --body "..."` with backticks in the body broke the drafter for a full workflow run. | Accuracy gap | Route any Claude-generated content (PR body, commit message, issue comment) to disk first, then use `--body-file` / `-F`. Never pass LLM text through inline shell quoting. |
| TS compile failed when monkey-patching `server.tool` because `McpServer.tool` has a strict overload signature. | Accuracy gap | When wrapping strongly-typed SDK methods, capture the original as `: any` before rebinding, or the compiler will reject the generic forwarder. |
