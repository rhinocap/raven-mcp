RavenMCP · Technical Reference

Design intelligence, specified.

RavenMCP is a design-intelligence MCP server. Install it, point your coding agent at it, and it audits pages, layouts, and screens, generates design systems and tokens, and carries your taste across projects.

01

Get Started

Install · Connect · Use

Three steps from zero to a design-literate agent. No account required for the open-source tier; the hosted endpoint adds a shared taste graph for teams.

1 —

Install

Run npx @ravenmcp/cli install, or add the server to your MCP client config manually:

mcp.config.json
{
  "mcpServers": {
    "raven": {
      "command": "npx",
      "args": ["-y", "raven-mcp"]
    }
  }
}
2 —

Connect

Restart your agent. Raven's 70 tools are now available — your agent discovers them automatically over MCP.

3 —

Use it

Ask your agent to audit a page, generate a design system, or check contrast. It calls the right tool automatically — no tool names to memorize.

02

Tool Reference

70 tools · 9 layers

Raven provides 70 tools across 9 knowledge layers. Claude calls the relevant tool based on the task; the entries below show what each tool takes and returns.

Principles Layer — 3 of 8 tools shown

raven.get_principles § 2.1 #

Get design principles relevant to a UI context. Returns usability heuristics, Laws of UX, Gestalt principles, accessibility rules, typography, color theory, mobile UX, and responsive layout.

Parameters
contextstringrequired

What you're designing — e.g. "signup form", "pricing page", "mobile nav", "dark dashboard"

categorystringoptional

Filter to: nielsen-heuristics, laws-of-ux, gestalt, accessibility, typography, color-theory, mobile-ux, responsive-layout, d4d

formatstringoptional

"full" (default) | "checklist" | "brief"

Ask your agent
  • Build a pricing page
  • What accessibility rules apply to forms?
  • Check this against Nielsen's heuristics
raven.evaluate_design § 2.2 #

Evaluate a design description against UX principles. Returns relevant principles, potential violations, and improvement suggestions.

Parameters
descriptionstringrequired

Description of the design to evaluate

contextstringoptional

What the design is — e.g. "pricing page for SaaS product"

goalsstring[]optional

Array of evaluation goals — e.g. ["conversion", "accessibility", "mobile-usability"]

Ask your agent
  • This signup form has 8 fields, no social login, and the button says Submit. Evaluate it for conversion.
raven.get_d4d_framework § 2.3 #

Get Design for Delight (D4D) templates — customer problem statement, ideal state, hypothesis, LOFAs, and experiment design.

Parameters
stagestringoptional

"frame" | "empathy" | "broad" | "narrow" | "experiment"

Ask your agent
  • Frame this feature as a customer problem statement
  • Draft LOFAs for the onboarding redesign

Audit Layer — 2 of 14 tools shown

raven.audit_contrast § 2.4 #

Check WCAG contrast across a live page or a raw color set. Returns every failing pair with its measured ratio, the element it was found on, and a token-preserving fix suggestion.

Parameters
targetstringrequired

A URL to audit, or an inline list of foreground/background pairs

levelstringoptional

"AA" (default) | "AAA" — the WCAG conformance level to test against

include_fixesbooleanoptional

Suggest the nearest passing color that stays on your token scale (default true)

Ask your agent
  • Audit this pricing page for contrast issues
  • Does this palette pass AAA on dark backgrounds?
raven.audit_page § 2.5 #

Full-page design audit: layout, hierarchy, spacing rhythm, typography, tap targets, accessibility, and consistency in one pass. Returns severity-ranked findings with a summary score.

Parameters
urlstringrequired

The page to audit — local dev servers work

viewportstringoptional

"desktop" (default) | "tablet" | "mobile" — or an explicit width

focusstring[]optional

Limit to specific checks — e.g. ["typography", "tap-targets"]

Ask your agent
  • Audit localhost:3000 before I ship it
  • Why does this page feel cramped on mobile?

Systems Layer — 1 of 9 tools shown

raven.generate_design_system § 2.6 #

Generate a complete design system — color tokens, type scale, spacing, radii, and component guidance — from a written brief or an existing brand. Bound taste profiles apply their overrides automatically.

Parameters
briefstringrequired

The product and its register — e.g. "calm fintech dashboard, dark-first, dense data"

brandobjectoptional

Existing brand constraints: locked colors, typefaces, or an existing token file to extend

formatstringoptional

"tokens" (default) | "css-vars" | "tailwind" | "full-spec"

Ask your agent
  • Generate a token set for this brand and wire it into the CSS
  • Extend our existing tokens with a data-viz palette

04

Data Structure

Response Shape

Every audit returns a structured object: findings[] with severity, rule, location, and fix, a summary score, and a calibration_hint when a taste profile is bound. Structure over prose — your agent acts on it directly.

  • findings[] array

    One entry per issue. Each carries severity (error | warn | info), the rule that fired, a CSS-selector location, and a concrete fix.

  • summary object

    A 0–100 score plus counts by severity — stable across runs, so agents can gate CI on it.

  • calibration_hint string · when bound

    Present when a taste profile is bound to the project: which profile applied and how many of its rules participated in the audit.

audit response
{
  "findings": [
    {
      "severity": "error",
      "rule": "contrast-minimum",
      "location": ".plan-card .price-note",
      "fix": "Raise text to #A9AFB8 — 4.5:1 on --bg-raised"
    },
    {
      "severity": "warn",
      "rule": "tap-target-minimum",
      "location": ".footer-links a",
      "fix": "Increase hit area to 44×44px"
    }
  ],
  "summary": { "score": 82, "errors": 1, "warnings": 3 },
  "calibration_hint": "profile 'andrew' bound — 2 taste rules applied"
}
05

Design Tokens

Generate · Extend · Enforce

Raven generates a full token set — color, type, spacing, radius — from a written brief or your existing brand, and every audit reads those tokens back to check that the built page actually uses them. Bound taste profiles apply per-project overrides, so a team's recorded decisions carry into every generated scale.

tokens.json · excerpt
{
  "color": {
    "bg-base":      "#0B0C0E",
    "bg-surface":   "#121417",
    "text-primary": "#E8EAED",
    "text-muted":   "#9AA0A8",
    "accent":       "#5B8CFF"
  },
  "space": [4, 8, 12, 16, 24, 32, 48, 64],
  "radius": { "sm": 4, "md": 8, "lg": 12 }
}
Rendered from the token file
bg-base#0B0C0E
bg-surface#121417
text-primary#E8EAED

accent#5B8CFF

Generated scales come back with contrast pre-verified — every text/background pairing in the set passes the level you asked for, so the palette is safe before the first component is built.

06

FAQ

Plain Answers

Does this replace a design system?

No. It reads and enforces the one you have. If you don't have one yet, it can generate a starting point — which then becomes the thing it enforces.

Does it work with any coding agent that supports MCP?

Yes. Raven is a standard MCP server — Claude Code, Cursor, Windsurf, or anything else speaking MCP over stdio or the remote endpoint.

Is my design data used to train models?

No. Audits run against Raven's knowledge base at request time. Taste profiles and decisions stay in your storage and are never used for training.

What's the difference between the free and team tier?

The free tier is the full open-source server: every tool, single user, local storage. The team tier adds a shared decision graph, per-user auth, and admin controls on the hosted endpoint.

Can I self-host?

Yes. The npm package runs anywhere Node runs, and the remote endpoint can be deployed on your own infrastructure. The hosted endpoint is a convenience, not a requirement.
