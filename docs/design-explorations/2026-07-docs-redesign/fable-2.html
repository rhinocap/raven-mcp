RavenMCP · Technical Reference

Documentation

RavenMCP is a design-intelligence MCP server. Install it, point your coding agent at it, and it audits pages, layouts, and screens, generates design systems and tokens, and carries your taste across projects.

Version1.16
Tools70
Layers9
ProtocolMCP · stdio / remote
LicenseOpen source
01

Get Started

Three steps from zero to your agent making design-informed decisions. No account, no config beyond one JSON entry.

  1. 1

    Install

    npx @ravenmcp/cli install — or add Raven to your MCP client config manually:

  2. 2

    Connect

    Restart your agent. Raven's 70 tools are now available — your agent discovers them automatically over MCP.

  3. 3

    Use it

    Ask your agent to audit a page, generate a design system, or check contrast. It calls the right tool automatically — you never invoke a tool by name unless you want to.

02

Tool Reference

Raven provides 70 tools across 9 knowledge layers. Claude calls the relevant tool based on the task; the entries below show what each tool accepts and returns. Every entry follows the same anatomy: description, parameters, example prompts.

Principles Layer · 6 tools

get_principles

Tool 01 · Principles

Get design principles relevant to a UI context. Returns usability heuristics, Laws of UX, Gestalt principles, accessibility rules, typography, color theory, mobile UX, and responsive layout.

Parameters
contextRequiredstring

What you're designing — e.g. "signup form", "pricing page", "mobile nav", "dark dashboard".

categoryOptionalstring

Filter to: nielsen-heuristics, laws-of-ux, gestalt, accessibility, typography, color-theory, mobile-ux, responsive-layout, d4d.

formatOptionalstring

"full" (default) | "checklist" | "brief".

evaluate_design

Tool 02 · Principles

Evaluate a design description against UX principles. Returns relevant principles, potential violations, and improvement suggestions.

Parameters
descriptionRequiredstring

Description of the design to evaluate.

contextOptionalstring

What the design is — e.g. "pricing page for SaaS product".

goalsOptionalstring[]

Array of evaluation goals — e.g. ["conversion", "accessibility", "mobile-usability"].

get_d4d_framework

Tool 03 · Principles

Get Design for Delight (D4D) templates — customer problem statement, ideal state, hypothesis, LOFAs, and experiment design.

Parameters
stageOptionalstring

"frame" | "empathy" | "broad" | "narrow" | "experiment".

Audit Layer · 14 tools

audit_page

Tool 04 · Audit

Run a full-page design audit on rendered HTML or a live URL. Checks layout, hierarchy, contrast, tap targets, typography, and consistency in one pass; returns structured findings with per-finding fixes and a summary score.

Parameters
urlRequiredstring

The page to audit — a live URL or a local dev-server address.

viewportOptionalstring

"desktop" (default) | "mobile" | "both". Mobile runs at 390×844 and adds tap-target checks.

checksOptionalstring[]

Restrict to specific check families — e.g. ["contrast", "typography"]. Defaults to all.

projectOptionalstring

A bound taste surface. When set, findings include calibration_hint judged against that project's rules.

Systems Layer · 9 tools

generate_design_system

Tool 05 · Systems

Generate a complete token set — color, type scale, spacing, radius, motion — from a written brief or an existing brand. Output is ready to paste as CSS custom properties or a JSON theme file.

Parameters
briefRequiredstring

What the system is for — e.g. "calm fintech dashboard, dark-first, one accent".

from_brandOptionalstring

A brand profile name or URL to derive from instead of generating fresh.

formatOptionalstring

"css" (default) | "json" | "tailwind".

Taste Layer · 8 tools

record_taste_decision

Tool 06 · Taste

Record a design decision — what was chosen, what was rejected, and why — into a taste profile. Recorded decisions calibrate future audits and stop the same question being re-litigated across sessions and agents.

Parameters
profileRequiredstring

The taste profile to record into.

dimensionRequiredstring

Short key for what was decided — e.g. "accent-color", "nav-pattern", "voice-register".

chosenRequiredstring

What was picked.

rejectedOptionalstring

What was turned down — the highest-signal half of the record.

whyOptionalstring

One line of reasoning, in the decider's own words when possible.

03

Examples

What a Raven call actually looks like from inside an agent session: your prompt, the tool call your agent makes, and what comes back.

Example A · Contrast audit
Prompt

"Audit this pricing page for contrast issues."

Tool call audit_contrast({ url: "https://app.example.com/pricing", standard: "AA" })
Returns
3 findings · score 78/100 Error.tier-note — 2.9:1 on #0E0E11. Minimum 4.5:1. Fix: lighten to #9BA0B4. Warn.badge-popular — 4.2:1, passes large-text only. Fix: raise weight to 600. Warnfooter links — 4.4:1 on hover state. Fix: hover color #C9C9D4.
Example B · Token generation
Prompt

"Generate a token set for a calm fintech dashboard — dark-first, one accent."

Tool call generate_design_system({ brief: "calm fintech dashboard, dark-first, one accent", format: "css" })
Returns
42 tokens — 12 color, 8 type, 14 spacing, 4 radius, 4 motion — as paste-ready CSS custom properties, with a one-paragraph rationale per group and AA-verified contrast pairs.
Example C · Heuristic check
Prompt

"Check this signup form against Nielsen's heuristics."

Tool call get_principles({ context: "signup form", category: "nielsen-heuristics", format: "checklist" })
Returns
A 10-point checklist scoped to forms — visibility of system status (inline validation), error prevention (confirm before destructive), recognition over recall (labels stay visible) — each with a pass criterion your agent applies to the actual markup.
04

Data Structure

Every audit returns a structured object, not prose. Your agent can act on it mechanically — apply the fix, re-run, confirm the finding clears.

  • findings[]each with severity, rule, location, and a concrete fix
  • summarya score and grade for the whole surface
  • calibration_hintpresent when a taste profile is bound — how this surface's rules shaped the verdicts
05

Design Tokens

Raven generates a full token set — color, type, spacing, radius — from a written brief or an existing brand. Bound taste profiles apply per-project overrides, so the same brief produces different tokens for your portfolio than for your product site.

Tokens ship as CSS custom properties, JSON, or a Tailwind theme. Contrast pairs are verified before they leave the tool.

06

FAQ

Does this replace a design system?

No. It reads yours, audits against it, and can generate a starting point when you don't have one. The system stays yours.

Does it work with any coding agent that supports MCP?

Yes. Anything that speaks MCP — Claude Code, Cursor, Windsurf, custom clients. Raven is a standard MCP server over stdio or remote.

Is my design data used to train models?

No. Audits run against your content at call time and nothing you send is used for training. Taste profiles live in your own storage.

What's the difference between the free and team tier?

The open-source server is free, with the full toolset, forever. The team tier adds a shared hosted taste and decision graph with per-user auth, so decisions carry across people and agents.

Can I self-host?

Yes. The npm package and the .mcpb bundle run entirely on your machine. The hosted endpoint exists for teams who want shared state without running anything.
